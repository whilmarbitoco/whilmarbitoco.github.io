01First Five Minutes — Baseline Workflow

When you receive a memory image in a timed competition, resist the urge to dive into a single plugin. Build a quick situational picture first. The sequence below is designed to answer the minimum-viable questions within a few minutes so you know where to look next.

Workflow

StageWhat you doWhat you establish
1. Receive image Identify file, hash it, note size. Chain-of-custody record, file type, rough size estimate (small vs large affects performance choices).
2. Identify OS / arch vol -f <memory> windows.info Windows version, architecture (x86/x64), kernel build, image type. If this fails, you may have the wrong OS plugin or an unsupported format.
3. Establish process baseline vol -f <memory> windows.pslist
vol -f <memory> windows.pstree		 What processes existed; parent/child relationships; obvious outliers (unexpected parent, unusual name, weird path).
4. Quick network sweep vol -f <memory> windows.netscan Active connections, listening sockets, owning PIDs, remote IPs/ports. Obvious C2 destinations or unusual listeners.
5. Command line sweep vol -f <memory> windows.cmdline What commands were run; suspicious arguments; powershell/cscript/wscript/cmd.exe usage.
6. Quick injection scan vol -f <memory> windows.malfind Processes with executable/private memory that don't match known modules — a fast way to flag potential injection.
7. Pick a lead Choose the most suspicious artifact from steps 3-6. Your first investigative pivot: a PID, an IP, a command line, a suspicious DLL, a VAD region.
8. Follow the lead Apply the relevant scenario playbook (Sections 5-15). Corroborate, expand, and dump evidence as needed.
Why this order matters Process listing and network scanning are fast and high-yield. They give you PIDs, IPs, and command lines — the pivot points you'll use for everything else. Don't start by dumping a process you haven't characterized yet.
Time box the baseline In a competition, spend 3-5 minutes on steps 2-6. If nothing jumps out, re-run with a finer lens (e.g., windows.psxview, windows.psscan, windows.vadregexscan). If something does jump out, stop and investigate it — don't keep collecting baseline data.

02Memory & OS Fundamentals (Practical)

You don't need a textbook. You need to know enough to read Volatility output without being surprised. Each concept below is paired with what it is, why it matters, and what Volatility 3 can show me.

RAM vs Disk

What it is: RAM holds the live, working state of the system — running code, open files, network sockets, decrypted credentials, recently accessed data. Disk holds persistent state.

Why it matters: Memory captures artifacts that may never hit disk, or that were already erased from disk. A process can run entirely from memory; a credential can be stolen from LSASS without a file write; a file can be deleted but still present in a process's handle or a VAD mapping.

Volatility 3: Shows you the in-memory state — processes, DLLs, handles, network sockets, VADs, command lines, registry hives, strings, and more. It does not show you the post-shutdown disk state; if something was never in memory, Volatility won't find it.

Physical vs Virtual Memory

What it is: Physical memory is the actual RAM chips. Virtual memory is the per-process address space the OS presents to each process. The OS maps virtual pages to physical pages (or to disk, or to nothing).

Why it matters: A process sees its own contiguous virtual address space; the underlying physical layout is irrelevant to it. Malware can allocate virtual memory, write code into it, and mark it executable — all without touching a file on disk. Virtual Address Descriptors (VADs) describe these regions.

Volatility 3: windows.vadinfo, windows.vadwalk, windows.vadregexscan, windows.memmap — let you inspect virtual memory regions per process.

Virtual Address Spaces & Kernel vs User Space

What it is: Each process has its own user-mode virtual address space. The kernel has its own address space (or shares a portion in some configurations). User-mode code cannot directly access kernel memory; kernel-mode code can access both.

Why it matters: Most user-mode malware operates in a process's user space. Kernel-mode rootkits operate in kernel space and can hide from user-mode enumeration. Volatility can inspect both, but the plugins differ.

Volatility 3: windows.pslist (user processes), windows.modules / windows.modscan (kernel modules), windows.ssdt (system call table), windows.callbacks (kernel callbacks), windows.driverscan (kernel drivers).

Processes

What it is: An instance of a running program. The OS maintains a Process Object (EPROCESS in Windows) containing the process ID, image path, command line, credentials/token, VAD root, handle table, thread list, and more.

Why it matters: Processes are the primary unit of execution. If you can identify the right process, you can pivot to its command line, DLLs, handles, network sockets, memory, parent, and children.

Volatility 3: windows.pslist (walks the kernel process list), windows.psscan (scans for EPROCESS structures), windows.pstree (parent/child tree), windows.psxview (compares enumeration sources to find hidden processes).

Threads

What it is: A unit of execution within a process. A process can have many threads; each thread has its own stack, registers, and state.

Why it matters: Some malware creates threads for code execution (e.g., injected shellcode running in a new thread). Suspended threads can indicate delayed execution or stealth. Thread start addresses can reveal where code is running from.

Volatility 3: windows.threads (lists threads per process), windows.suspended_threads (threads in a suspended state), windows.suspicious_threads (deprecated; look for alternatives), windows.thrdscan (scans for threads).

Handles

What it is: A handle is a reference to a kernel object — a file, a registry key, a process, a thread, a mutex, a token, a section, a token, a window station, etc. A process's handle table tells you what objects it has open.

Why it matters: Handles reveal what a process is touching. A process with a handle to a registry key may be reading/writing persistence. A process with a handle to another process may be injecting or manipulating it. A process with a handle to a file may be exfiltrating it.

Volatility 3: windows.handles (lists open handles per process).

DLLs / Modules

What it is: A DLL (Dynamic Link Library) is a shared library loaded into a process's address space. A module is a broader term that includes DLLs, executable images, and kernel drivers. The Loader (LDR) tracks which modules are loaded into each process.

Why it matters: Loaded modules tell you what code a process is running. An unusual DLL in a legitimate process can indicate DLL injection. A missing module (compared to a known baseline) can indicate DLL unloading or hollowing. A kernel module can indicate a rootkit.

Volatility 3: windows.dlllist (loaded DLLs per process), windows.ldrmodules (LDR-reported modules), windows.modules (kernel modules), windows.modscan (scans for kernel modules), windows.malware.ldrmodules (LDR modules with malware focus).

Executable Memory & Memory Pages

What it is: Memory pages have protection flags: READ (R), WRITE (W), EXECUTE (X). Combinations like RW (read/write), RX (read/execute), and RWX (read/write/execute) describe a page's permissions. Legitimate software uses dynamic executable memory (e.g., JIT compilers, allocators), but RWX or executable-private memory is a red flag worth investigating.

Why it matters: Malware often allocates RWX or executable-private memory to run shellcode or injected code. Seeing a process with a memory region that is executable but not backed by a known module is a strong indicator of something worth investigating.

Volatility 3: windows.vadinfo (shows memory region protections), windows.malfind (finds executable-private memory and shows the code), windows.vadregexscan (searches VAD regions for patterns).

VADs (Virtual Address Descriptors)

What it is: A VAD is a kernel structure that describes a region of a process's virtual address space — its start address, end address, protection, and what (if anything) backs it (e.g., a mapped file, the PEB, a stack, an allocation).

Why it matters: VADs are the map of a process's memory. An unusual VAD — one with executable permissions that doesn't correspond to a loaded module — is a primary indicator of injection or shellcode. VADs also reveal memory-mapped files, which can be recovered.

Volatility 3: windows.vadinfo (lists VADs per process), windows.vadwalk (walks the VAD tree), windows.vadregexscan (scans VAD regions).

Process IDs & Parent/Child Processes

What it is: Each process has a unique PID (Process ID). Each process (except the initial system process) has a parent PID (PPID) — the process that created it. A process tree shows the creation hierarchy.

Why it matters: The parent tells you the context in which a process was created. explorer.exe spawning powershell.exe is different from svchost.exe spawning cmd.exe. A process with no parent, or a parent that doesn't exist in the list, is suspicious.

Volatility 3: windows.pstree (shows parent/child relationships), windows.pslist (shows PPID column).

Sockets / Network Objects

What it is: A socket is an endpoint for network communication. In memory, sockets are represented as kernel objects associated with a process. A TCP connection has a local address/port and a remote address/port; a listening socket waits for inbound connections.

Why it matters: Network connections are the bridge between the host and the outside world. A suspicious IP or port can be traced back to a PID, and from there to a process name, command line, DLLs, and memory.

Volatility 3: windows.netscan (scans for network connections), windows.netstat (lists connections similarly to the netstat command).

Registry Data in Memory

What it is: The Windows Registry is a hierarchical database stored in hives (files like SYSTEM, SOFTWARE, SAM, SECURITY, DEFAULT, and user hives like NTUSER.DAT). Portions of these hives are loaded into memory when the system runs.

Why it matters: Registry hives contain persistence mechanisms (Run keys, services, scheduled tasks), user information, recently used files, and configuration data. Hives in memory can be enumerated and printed without touching the disk image.

Volatility 3: windows.hivelist (lists registry hives in memory), windows.hivescan (scans for hives), windows.registry.printkey (prints keys), windows.registry.amcache (AMCache registry data), windows.registry.scheduled_tasks, windows.registry.userassist, windows.registry.certificates, windows.registry.getcellroutine.

Memory-Mapped Files

What it is: A file can be mapped into a process's virtual address space, allowing the process to access the file's contents via memory reads/writes. The VAD for a mapped file points back to the file.

Why it matters: Memory-mapped files can reveal files that were open but may no longer be on disk (deleted files, temporary files, files opened by malware). VADs that point to file objects can be dumped.

Volatility 3: windows.vadinfo (shows which VADs are backed by file objects), windows.dumpfiles (dumps file-backed memory regions), windows.filescan (scans for file objects in memory).

Process Injection Concepts

What it is: Code running in a process's address space that was not part of the original executable. Common forms: DLL injection (loading a malicious DLL into a process), shellcode injection (writing code into memory and executing it), process hollowing (creating a process in a suspended state, unmapping its legitimate image, and replacing it with malicious code), thread injection (creating a thread in another process).

Why it matters: Injection lets malware run under the identity of a legitimate process, evading process-name-based detection. A svchost.exe doing something suspicious may actually be a hollowed or injected process.

Volatility 3: windows.malfind (detects executable-private memory typical of injection), windows.hollowprocesses (detects process hollowing), windows.processghosting, windows.pebmasquerade (detects PEB path mismatches), windows.malware.psxview (compares process enumeration sources), windows.vadinfo / windows.vadregexscan (inspect VADs for injected regions).

Volatile vs Non-Volatile Evidence

What it is: Volatile evidence exists only while the system is running (or in a memory capture taken while running). Non-volatile evidence persists on disk across reboots.

Why it matters: Memory captures volatile evidence that disk forensics may miss: running processes, network connections, decryption keys in memory, command lines of running processes, recently decrypted data, and artifacts that were deleted from disk but are still in memory.

Volatility 3: Everything Volatility shows you is memory-resident evidence. It complements, but does not replace, disk forensics.

03Image Triage Checklist

When you receive a memory image, do these steps before running analysis plugins. They take under a minute and prevent wasted time.

Checklist

StepCommand / actionWhat it establishes
File identification file <memory>
ls -lh <memory>		 Confirm it's a raw/memory dump (not a text file, not a compressed archive, not the wrong image). Note size — large images may require performance tuning.
Hashing sha256sum <memory> Record the hash for chain-of-custody and to confirm you're working on the correct image. Hash the file once; don't re-hash during analysis.
Volatility identification vol -f <memory> windows.info OS version, architecture, kernel build, number of processors, image type. This is the single most important first command. If it fails, do not run Windows plugins — the image may be Linux, macOS, or an unsupported format.
Basic sanity check vol -f <memory> windows.pslist Confirm the image yields process data. If windows.info succeeds but pslist produces nothing, the image may be corrupted or the process list may be damaged. Try windows.psscan as a fallback.
Symbol readiness Run a plugin that needs symbols (e.g., windows.info). Volatility 3 auto-fetches ISF symbol files by default when online. If offline, some plugins will work without external symbols (VAD, process list, netscan), while others (dumping PEs with pedump, verinfo) may need them. When in doubt, test a plugin and see if it errors about symbols.

What each command tells you

  • file — confirms the file type (RAW memory dump, crash dump, hibernation file, etc.). If it says "data" with no further detail, that's normal for raw dumps.
  • sha256sum — produces a reproducible identifier for the image. Use it in your notes.
  • windows.info — tells you whether Volatility understands this image and what OS/architecture it is. If this says the image is Linux, switch to linux.* plugins immediately.

Troubleshooting triage

SymptomWhat to try
windows.info fails / no output Image may be Linux or macOS — try linux.info (Linux) or check if it's a Mac image. Image may be corrupted. Image may be an unsupported acquisition format (e.g., a compressed or encrypted dump). Verify with file.
windows.info succeeds but pslist is empty The process list (EPROCESS chain) may be damaged. Try windows.psscan (scans for EPROCESS signatures rather than walking the chain). Try windows.psxview to compare enumeration methods. Image may be too corrupted to recover processes.
Plugin says "symbol" error Some plugins need symbol files. Volatility 3 fetches ISF files automatically when online. If offline, basic plugins (pslist, netscan, vadinfo) often still work; symbol-heavy plugins (pedump, verinfo, some registry plugins) may fail. Check the plugin's help: vol <plugin> --help.
Wrong OS assumption Stop running Windows plugins. Run windows.info to confirm; if it says Linux, use linux.* plugins; if it says macOS, use the appropriate macOS plugins. Don't force Windows plugins on a non-Windows image.
Unsupported acquisition format Volatility 3 supports raw dumps, crash dumps, hibernation files, and some hypervisor formats. If the image is from an unfamiliar tool, check file output and Volatility's documentation. You may need to convert the image first.
Analysis is slow Use --parallelism processes to enable multiprocessing. Narrow the scope — don't run every plugin. For large images, avoid scanning plugins unless necessary. Consider filtering output. See Section 17 for performance tips.
Image is huge (hundreds of GB) Time-box your analysis. Use the most targeted plugins first. netscan, pslist, cmdline are usually fast. malfind, vadregexscan, yarascan can be slow on huge images. Prioritize the investigative question over exhaustive scanning.

16Cross-Correlation — Joining Evidence

The strongest conclusions come from correlating multiple artifact types. A single artifact in isolation is a lead; multiple artifacts that converge on the same conclusion are evidence.

Correlation model: PID as the hub

PID: <1234> ├── Process name: <name>.exe ├── Parent PID: <PPID> → parent process name ├── Command line: <full command line> ├── DLLs: <list of loaded DLLs> ├── Handles: <files, keys, processes, tokens> ├── Network connections: <local/remote IP:port, state> ├── Memory regions: <VADs, protections, backing> └── Dumped artifacts: <recovered files, dumped memory>

Correlation model: IP as the hub

IP: <192.0.2.1> ↓ Connection in netscan Connection: <protocol, local port, remote port, state, PID> ↓ Owning PID PID: <PID> ↓ Process Process: <name, command line, parent, DLLs, handles, memory> ↓ Further artifacts ├── Command line analysis ├── DLL investigation ├── Memory / VAD inspection ├── Injection analysis ├── Persistence check └── Dump evidence

Correlation model: command line as the hub

Command line: <suspicious command> ↓ Found in cmdline plugin Process: <PID, name, parent> ↓ PID ├── DLLs ├── Handles ├── Network connections ├── Memory regions └── Dump
The golden rule of correlation Never analyze artifacts in isolation. Every PID should be cross-referenced with its command line, parent, DLLs, handles, network, and memory. Every IP should be traced back to a PID and then to the full process context. Every suspicious DLL should be tied to the process that loaded it, the command line that launched it, and any network or memory activity associated with it.

Practical correlation workflow

StepAction
1. CaptureFor each artifact of interest, record the raw output (PID, IP, DLL name, VAD address, key path, etc.).
2. LinkLink artifacts by their shared identifiers: PID, PPID, IP address, port, file path, registry key, DLL name.
3. ExpandFor each linked artifact, expand outward: a PID leads to command line, parent, DLLs, handles, network, memory. An IP leads to PID, process, command line, DLLs, memory.
4. ConvergeLook for convergence: do multiple artifact types point to the same conclusion? A process with a suspicious command line, injected code, and a network connection to an external IP is more suspicious than any one alone.
5. DocumentDocument the correlation chain. This is what turns a collection of plugin outputs into a coherent finding.
6. TestTest yourHypothesis against the evidence. Does the evidence support it? Are there alternative explanations? What would disprove it?

17Troubleshooting

When a plugin doesn't work, produces no output, or gives unexpected results, work through these checks before assuming the image is bad or the plugin is wrong.

"The plugin doesn't work."

Possible causeWhat to try
Wrong OS pluginCheck windows.info. If the image is Linux, use linux.* plugins; if macOS, use macOS plugins. Don't force Windows plugins on a non-Windows image.
Unsupported image formatRun file <memory>. Volatility 3 supports raw dumps, crash dumps, hibernation files, and some hypervisor formats. If the format is unfamiliar, check Volatility documentation or convert the image.
Symbol problemSome plugins need symbol files. Volatility 3 fetches ISF files automatically when online. If offline, basic plugins often still work; symbol-heavy plugins may fail. Check the plugin's error message for symbol-specific wording. Run vol <plugin> --help for plugin-specific options.
Incorrect plugin nameVerify the plugin name with vol --help. Plugin names are case-sensitive and dotted (e.g., windows.pslist, not pslist or WindowsPsList).
Malformed commandCheck the syntax: vol -f <memory> <plugin> [options]. Ensure the memory file path is correct. Check for typos in the plugin name and options.
Insufficient permissionsEnsure you can read the memory image file. Ensure the output directory is writable (for dumping plugins).
Corrupted imageIf windows.info succeeds but process plugins fail, the image may be partially corrupted. Try scan-based plugins (psscan, hivescan, filescan) which are more resilient than list-walking plugins.
Plugin limitationsSome plugins only work on specific Windows versions or configurations. Check the plugin's help and Volatility documentation. Some plugins are deprecated or have known limitations.

  • Consider whether you need the full image or whether a subset (if available) would suffice for the investigative question.
  • Avoid vadregexscan and yarascan on huge images unless you have a specific target — they can be very slow.

How to use these Treat each scenario as a timed exercise. Start with the given finding, work through the relevant playbooks, and document your findings. Answer Key — Guidance, Not Solutions

These are not "answers" to memorize — they are the kinds of things you should look for and the investigative logic you should apply. Your actual findings will depend on the specific memory image.

Scenario 1 — Suspicious PowerShell
What to look for: The PID from pslist. The parent from pstree — is it a user process (expected) or a service/system process (unexpected)? The command line from cmdline — look for -Enc, -E, -NoP, -NonI, -W Hidden, -ExecutionPolicy Bypass, IEX, DownloadString, or any encoded/obfuscated content. Network connections from netscan — did the PowerShell process connect to an external IP? DLLs from dlllist — anything unusual loaded into powershell.exe? Memory from vadinfo / malfind — any executable-private memory?
Next pivot: If the command line is encoded, decode it (offline) and analyze it. If there's a network connection, follow the Suspicious IP Playbook. If there's injected code, follow the Injection Playbook. If the parent is suspicious, investigate the parent.
Scenario 2 — Suspicious C2
What to look for: The owning PID from netscan. The process name and parent from pslist / pstree. The command line — does it explain the connection (e.g., a download, a beacon, a reverse shell)? DLLs — anything that suggests malware (unusual paths, injected modules)? Memory — any executable-private regions? Persistence — does the process or its parent have services, scheduled tasks, or registry Run keys that would restart it?
What supports malicious activity: A process with an encoded/obfuscated command line, a network connection to an unusual external IP, injected code, and persistence mechanisms all pointing to the same process is strong evidence of malware. A process with just a network connection to an unusual IP but a benign command line and no other indicators may have a benign explanation (e.g., a legitimate application reaching an unexpected server).
Scenario 3 — Process Injection
What to look for: The process from malfind. The VAD region's protection (RWX is highly suspicious; RX private is also suspicious). Whether the region is backed by a module or file (if it is, it may be less suspicious; if it's private, it's more suspicious). DLLs — any unusual modules? Command line and parent — do they provide context? Hollowing/masquerading checks — any image path mismatches?
What supports the injection hypothesis: A process with executable-private memory (especially RWX), no corresponding module backing the region, an unusual command line, and network activity is a strong injection candidate. A process with RWX memory but a legitimate command line and expected DLLs may be a false positive (e.g., a JIT compiler or a game engine).
Scenario 4 — Hidden Process
What to look for: Processes that appear in psscan but not pslist (or vice versa). Use psxview to systematically compare sources. For each discrepant process, check whether it has a valid command line, DLLs, handles, and network connections. A real hidden process will typically have some of these artifacts; a false positive from the scan may have none.
Why the discrepancy matters: If a process is hidden from the linked-list walk but visible in the scan, a rootkit may have unlinked it. This is a strong indicator of advanced malware. However, memory corruption can also cause discrepancies. Corroborate with other artifacts before concluding.
Scenario 5 — Malware Triage
What to look for: Start with windows.info to confirm the OS. Then pslist and pstree for the process baseline. netscan for network connections. cmdline for command lines. malfind for injection indicators. From these five plugins, you should have a good picture of the system's state and can identify suspicious artifacts to investigate further.
Building aHypothesis: Look for convergence. A suspicious process + suspicious command line + suspicious network + suspicious memory is a strongerHypothesis than any one alone. Document what you find, what you don't find, and what you would need to investigate further. TheHypothesis should be testable against the evidence.
